# Glossary Reference Library Design

**Date:** 2026-08-31
**Status:** Approved design

## Summary

Turn the glossary into a hybrid reference library. Every term remains useful as a short, plain-language definition in the glossary index and inline hover cards. Selected terms can grow into detailed, source-backed reference articles without changing that concise definition.

The first release will add instant search, A–Z and category filtering, optional term imagery, long-form entry navigation, related terms, and one exemplary article for Electrical Conductivity (EC). The site remains statically generated by Astro and does not add a client framework, backend search service, or pagination.

## Goals

- Make a growing glossary fast to browse by name, alias, subject, or plain-language definition.
- Preserve concise definitions as a stable contract for index entries, hover cards, metadata, and entry-page ledes.
- Support optional Wikipedia-like depth through the existing Sanity Portable Text workflow.
- Promote substantial entries visually without making imagery mandatory for every term.
- Keep the glossary usable as semantic HTML before JavaScript loads.
- Establish one complete editorial example with the EC entry before expanding other terms.

## Non-goals

- Expanding every glossary term into a long-form article in the first release.
- Numbered pagination.
- Searching full Portable Text bodies.
- Adding React, Preact, Svelte, or a third-party search service.
- Building structured footnotes or a citation database.
- Replacing Portable Text with Markdown.

## Product Direction

The glossary has two complementary layers:

1. **Quick reference:** every term has a canonical name and self-contained definition of no more than 200 characters. This is the content shown in the index and hover cards.
2. **Detailed reference:** important terms may include an image and a substantial Portable Text article with headings, inline source links, related terms, and references.

The index leads with a small **In-depth guides** row for explicitly featured entries, followed by the complete text-first directory. An entry earns visual promotion only after its long-form content and image are complete.

## Content Model

The existing `glossaryTerm` fields remain:

- `term`: required canonical display name.
- `slug`: required page slug.
- `shortDefinition`: required self-contained definition, maximum 200 characters.
- `body`: optional Portable Text article.

Add these fields:

- `image`: optional Sanity image with hotspot support. Its inline `alt` field is required when an image is present.
- `aliases`: optional array of unique nonempty strings. Aliases participate in search but do not replace the canonical term.
- `category`: required controlled string value.
- `relatedTerms`: optional unique references to other `glossaryTerm` documents. A term cannot reference itself.
- `featured`: optional boolean, defaulting to false in the Studio.
- `lastReviewedAt`: optional date displayed on detailed entries.

The initial category set is:

- Plant Biology
- Cultivation
- Environment
- Nutrition
- Chemistry
- Post-Harvest
- Business & Regulation

Category values and labels must come from `shared/glossary-categories.ts`, imported by both the Studio schema and frontend. The stored values are stable slugs, while labels remain presentation data. The shared file follows the root TypeScript style and is not duplicated inside the separately formatted `studio/` project. This prevents filters, queries, and editor options from drifting apart.

Studio validation must reject a featured term unless it has:

- a nonempty Portable Text body;
- an image;
- image alt text; and
- a reviewed date.

The frontend repeats these checks at build time because Studio validation does not protect existing documents or API writes. Build errors must name the offending document ID and missing field. The site must not silently substitute an “Uncategorized” value, omit malformed featured cards, or invent fallback copy.

## Electrical Conductivity Exemplar

Electrical Conductivity becomes the first complete reference article. It will receive:

- the Nutrition category;
- aliases including `EC`;
- one image with editorially chosen hotspot and visitor-facing alt text;
- a reviewed date;
- related glossary-term references;
- a heading-structured Portable Text article;
- inline external source links; and
- a manually authored References section.

The article establishes the editorial pattern for later entries. It does not create a fixed section template that every subject must follow.

## Data Layer

Extend the glossary summary projection with the fields needed by the index: aliases, category, featured state, and image metadata. Image projections must include `asset->`, `alt`, `crop`, and `hotspot`; declaring hotspot support in the Studio schema without projecting crop and hotspot would discard the editor's chosen framing.

Extend the detail projection with the same fields plus `body`, related-term summaries, reviewed date, and existing mention backlinks.

Introduce narrow runtime validators at the Sanity boundary. All terms require a recognized category. Featured terms require the complete featured-entry contract. Validation happens during the Astro build, so malformed content blocks both code-triggered and content-triggered deployments.

The index receives all compact term records at build time. No endpoint or separately fetched JSON index is required at the current collection size.

## Glossary Index

The server-rendered index contains:

1. Page title and explanatory subtitle.
2. A real labeled search input.
3. A–Z controls.
4. Single-category controls.
5. A live result count and clear-all action.
6. An **In-depth guides** row of explicitly featured entries.
7. The complete alphabetical text directory.
8. The existing link to the separate terpene section.

The featured row uses the optional term image, category, canonical term, and a short editorial teaser derived from the short definition. It is hidden whenever search, letter, or category filters are active so filtered results remain visually direct.

Directory entries remain text-first and display the canonical term, short definition, and category. They do not show thumbnails. This keeps entries without images intentional and makes the list quick to scan.

### Search and filters

Search matches normalized values from:

- canonical term;
- aliases;
- short definition; and
- category label.

It does not search the full article body. Normalization applies Unicode NFKD normalization, removes combining marks, lowercases, converts punctuation runs to spaces, collapses whitespace, and trims. Filters combine: a query, letter, and category can all narrow the same result set.

State is reflected in URL parameters, for example:

```text
/glossary/?q=conductivity&category=nutrition
```

Reloading a filtered URL and using browser back or forward must restore the interface. Typing replaces the current history entry so each keystroke does not create a navigation stop; discrete letter, category, and clear actions push history entries. Invalid query parameter values are rejected from interface state and removed when the URL is next synchronized rather than being silently treated as real filters.

No-JavaScript behavior remains the complete alphabetical glossary. Progressive enhancement adds filtering; it does not own the content.

### Accessibility and responsive behavior

- The search input has a visible label.
- Filter controls are native buttons with `aria-pressed` state.
- Result-count changes use a polite live region.
- Filtered entries are removed from visual display and keyboard navigation.
- The clear action is keyboard accessible and receives focus only through normal navigation.
- On narrow screens, entries stack and A–Z controls scroll horizontally with usable target sizes.
- An empty result set shows the active search term, suggests clearing filters, and exposes a clear-all control.

## Individual Term Page

Detailed entries use a reference-first layout:

- breadcrumb and category;
- canonical term title;
- short definition as the lede;
- optional image beside the title;
- reviewed date and estimated reading time when a long body exists;
- sticky table of contents on desktop;
- Portable Text article;
- related terms;
- existing **Mentioned in** backlinks; and
- return-to-glossary link.

When no image exists, the title and lede expand into the available hero space. The page must not render an empty image shell. When no long body exists, the page omits reading time and the table of contents and remains a complete concise entry rather than displaying empty article furniture. Reading time counts plain text extracted from Portable Text and rounds up at 200 words per minute, with a minimum of one minute.

The table of contents is derived from `h2` and `h3` Portable Text blocks. One shared heading-extraction helper must generate both article IDs and navigation targets. It must create deterministic slugs and suffix collisions so repeated or punctuation-equivalent headings cannot produce duplicate IDs. The existing built-output anchor checker remains the final guard.

At desktop sizes the contents navigation occupies a narrow sticky column beside the reading column. It becomes a compact inline contents block on smaller screens.

References remain ordinary Portable Text under an editor-authored References heading, using the existing inline URL annotation. Related terms remain Sanity references so their routes follow current document slugs rather than duplicating URLs in content.

Metadata continues to use `shortDefinition`. The page also emits defined-term structured data alongside the existing breadcrumb structured data, using the canonical URL and available aliases.

## Client Architecture

Use progressive enhancement rather than a hydrated framework component.

A dependency-free TypeScript module owns pure search behavior:

- searchable-text normalization;
- term matching;
- letter and category filtering;
- URL filter parsing and serialization; and
- result ordering.

A thin browser controller owns DOM concerns:

- reading controls and term data attributes;
- invoking the pure filter functions;
- hiding and revealing entries;
- updating pressed states and result counts;
- hiding the featured row while filters are active;
- synchronizing `history.pushState` or `history.replaceState`; and
- responding to `popstate`.

The pure module must not know about DOM nodes. The controller must not reimplement matching rules. This shares the search mechanic while keeping page orchestration separate.

## Failure Behavior

- An unknown category fails the build with the term ID and invalid value.
- A featured term missing body, image, alt text, or review date fails the build with all missing requirements.
- An unresolved related-term reference fails the build rather than rendering a link to nowhere.
- A malformed URL filter is not activated and is removed on the next state synchronization.
- Search code must handle zero terms and zero matches explicitly.
- Client enhancement failure leaves the complete server-rendered glossary visible.

## Rollout Sequence

The release order is load-bearing:

1. Add the shared categories and new Studio fields, including validation.
2. Deploy the Studio schema.
3. Assign a primary category to every published glossary term.
4. Author and publish the complete EC exemplar, including its image and related references.
5. Confirm the content dataset satisfies the frontend contract.
6. Merge and deploy the frontend changes.

The frontend must not merge before the category backfill. Existing published documents are not automatically made valid when a Studio rule becomes required.

## Verification

Add dependency-free Node 22 checks for the pure search module, following the existing `check-drop-lookup.ts` pattern. Cover:

- canonical-term matches;
- alias matches;
- short-definition matches;
- category-label matches;
- case, Unicode, whitespace, and punctuation normalization;
- combined query, letter, and category filters;
- stable alphabetical ordering;
- valid and invalid URL state;
- empty collections; and
- zero-result searches.

Add a Make target and CI job for these checks. Production-build assertions must verify:

- complete no-JavaScript glossary markup;
- featured-card content and image alt text;
- index search/filter hooks;
- EC table-of-contents links and matching article IDs;
- related-term links;
- concise entries without images or bodies; and
- defined-term and breadcrumb structured data.

Run the existing CI-equivalent checks before opening the implementation PR:

- formatter;
- root lint;
- `yarn astro check`;
- Studio lint, type check, and format check;
- production build against real Sanity content;
- content-style check;
- heading-anchor check;
- analytics check;
- navigation check; and
- internal-link validation.

Because repository policy forbids starting another development server, interaction verification happens against the user's existing local server. Verify instant search, combined filters, URL restoration, keyboard operation, responsive layout, empty results, and hotspot crops there.
